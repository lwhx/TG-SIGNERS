# P3：运行性能、历史保留与转发告警

2026-10-14 实施于 P2 基线 `ef3281179907552945a685007f0523203696e4f0`。继续使用原 Dashboard、单容器、单实例和 `./data:/data`；无需新数据库或环境变量。

## 性能与 Dashboard

- 概览按统计时区在 SQLite 聚合近七天计数，返回至多七天 × 状态数的结果；不再将全部运行记录载入 Python。
- 概览最近六条记录不查询/返回大字段 `response`；完整回复仍从「日志与终端」查询。
- 转发历史复用已初始化的 Ledger，避免每次 HTTP 查询重新申请迁移写锁；增加更新时间索引和 WAL 并发读写。
- 页面轮询串行执行，上一轮结束后才开始计时；离开页面/更换筛选取消旧请求，隐藏标签页暂停轮询，恢复可见时立即检查。
- 仅概览页面查询概览统计。转发记录每 20 秒、统计每 60 秒刷新；切换状态/页码不重新查询统计。
- 显示最近同步时间、保留错误提示，提供重置筛选和每页 20/50/100 条；历史缩减后自动修正页码。

## 历史保留

入口：**系统设置 → 运行与历史保留**。先保存策略，再预览；启用后可点击「清理一批历史」，手动清理需确认。定时清理每小时执行一次，不在启动时立即删除。

| 配置 | 默认 | 范围/说明 |
| --- | --- | --- |
| 启用清理 | **关闭** | 未启用时手动清理返回 409，定时作业不删除 |
| 执行历史 | 90 天 | 7–3650 天；只处理非 running 且有结束时间的 Run |
| 成功转发详细历史 | 90 天 | 7–3650 天；按最近更新时间 |
| 失败转发详细历史 | 180 天 | 30–3650 天；按最近更新时间 |
| 每批上限 | 各 500 条 | 每次最多 500 条执行历史 + 500 条转发详细历史 |

从不清理账号、Session、密码、密钥、任务配置、自动化状态或上游签到记录 `data/upstream/data.sqlite3`。`sending` 转发记录即使很旧也不删除，不自行推断其是否已经送达。

成功投递的去重标记保存在同一个转发数据库 `relay_dedup` 表，长期保留最小的目标与指纹；创建标记和删除详细记录在同一写事务中完成。清理后再次收到相同消息仍返回 duplicate。旧版未知 dedup 的成功行也保守保留标记；明确 `dedup=off` 的行无需保留标记。失败历史被清理后不再提供人工重试，后续再次遇到该消息可按当前规则执行。

统计基于尚保留的详细记录，并非永久累计总数。清理后 SQLite 空间可供复用，文件不一定立刻变小；不自动运行阻塞式 VACUUM。详细历史删除无法从面板撤销，启用前按现有部署文档备份完整 data。

## 转发异常告警

入口同上，实际渠道仍在 **系统设置 → 消息通知** 配置并保存。没有启用的渠道时不会发送或占用冷却。告警默认启用，初次回看 5 分钟（1–60），全局冷却 30 分钟（5–1440）。

- 每分钟独立检查投递 Ledger，将当前仍失败且尚未通知的记录按账号、任务、错误类型合并；每份显示总量和最多十组摘要，不包含目标、消息正文或凭据。
- 初次激活使用回看窗口，避免旧记录集中通知；P1/P2 历史行不会被标为新失败。第一次告警之后使用持久失败序号游标，冷却或重启期间积压的新失败在下一次允许时合并通知，不会因超过回看窗口而丢失。
- 同一失败未发生新尝试且已经通知成功，不重复提醒。重试再次失败会产生新序号；检查前已恢复成功的行不再告警。
- 发送前先持久化冷却，避免并发和重启刷屏。任一渠道成功即推进确认游标，避免正常渠道因另一个故障渠道反复收到同一告警；全部失败保留游标，冷却后重试。服务恰好在外部通知成功、游标提交前崩溃时仍可能重复一次，跨服务无法保证 exactly-once。
- 通知 HTTP 沿用原每渠道超时。定时作业 `max_instances=1`，通知失败或缓慢不会阻塞消息发送。已有签到/Session 通知不变；转发投递错误由汇总替代逐条通知，其他自动化错误保留原处理。

## API 与数据兼容

所有维护接口继承管理员鉴权、同源写入校验及 no-store：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/maintenance` | 策略、最近清理、告警状态 |
| PUT | `/api/maintenance/policy` | 保存完整策略，数值由 Pydantic 校验 |
| GET | `/api/maintenance/preview` | 只读统计全部符合条件的详细历史数量 |
| POST | `/api/maintenance/cleanup` | 按已保存且启用的策略清理一批 |

Dashboard 主库沿用原表，维护设置写入既有 settings。转发库仅追加 `failure_seq` 字段、索引及两个辅助表；原行不删改，首次初始化后缓存 Ledger 对象，不复用 SQLite 连接跨线程。升级/回滚按 `docs/GHCR-DEPLOY.md` 的停机完整备份执行。
