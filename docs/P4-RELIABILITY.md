# P4：转发可靠性设计与操作说明

目标：先准确区分已送达、明确失败、发送中和结果待核查，再为明确可恢复的失败提供有界重试。保留原 Dashboard、单容器、账号/任务/Session 和现有 data 目录。

## 发送边界

- 新增 `uncertain`（待核查）。网络错误、超时、取消、未知异常以及过期发送租约不代表明确未送达；不自动重发，也不允许普通人工重试绕过。
- 正常重复消息不会直接重试已有失败；需通过人工操作或启用自动队列。正常发送复用统一 Telegram 限速包装器；Dashboard 转发上下文每次底层 RPC 只尝试一次，关闭 SDK 内部 FloodWait 等待与重试，避免多次底层尝试混淆最终状态。签到和其他工具调用维持原设置。若发送 RPC 已返回成功，随后高层解析或附加读取失败，仍转待核查，禁止按临时拒绝自动重发。
- 只有该单次尝试上下文里的 Telegram 明确拒绝响应可归类为失败。FloodWait 为可恢复；权限、目标、账号等其他明确 RPC 拒绝为永久错误。SDK 吞掉的服务端错误最终变成超时，仍按待核查处理。
- P1–P3 旧失败缺少明确失败分类，不加入自动队列；有溯源信息的旧失败需先核查。旧成功行及去重标记保持有效。
- 管理员核对目标聊天后，可确认已送达，或确认未送达。后者只解锁人工重试，不立即发送。确认使用记录的尝试次数作并发保护，保留确认类型与时间。进程内仍活跃的发送即使租约过期也不能被确认解锁；同一次尝试的迟到成功证据覆盖“未送达”，原确认仍留在审计表。

## 自动重试

- 仅 `text/extract/template` 的明确临时拒绝参与自动重试，发送校验过的文本快照；`forward/copy` 仅人工重试，不进入自动队列。
- 全局默认关闭；通过「系统设置 → 转发可靠性」启用/暂停。每条失败记录也可暂停/恢复。
- 默认最多 3 次自动处理，每轮最多 5 条，调度间隔 30 秒。每次重新验证原账号、启用的任务、配置摘要、来源消息、筛选与原始内容哈希，复用 P2 安全重试路径。源摘要独立包含完整文字、实体、编辑时间和媒体身份，提取输出相同也不能绕过来源编辑检查。`copy` 使用已核验的 Message 快照；原生 `forward` 依赖 Telegram 消息引用，人工检查与实际转发之间仍可能发生服务器侧编辑，因此不支持自动重试。旧 forward/copy 内容摘要不升级补造，摘要不符时停止人工重试。
- 默认指数延迟基数 60 秒、上限 3600 秒；目标已有冷却和 Telegram 要求的等待时间作为额外下限，不因上限被缩短。只处理最近 24 小时的失败。
- SQLite 持久保存排期、自动次数、暂停状态与取件令牌。取件后崩溃，发送前可在租约到期后恢复；发送后崩溃则转待核查，不猜测是否送达。
- 人工重试、实时监听与自动处理共享原子保留锁；已成功和待核查记录始终不可被队列发送。配置/来源变化停止该记录自动处理，次数用尽后保留失败详情。
- 清理跳过发送中、待核查、旧未分类失败及仍有自动排期的记录；成功去重标记继续长期保留。其他失败详情清理时保存最小拦截指纹，防止删除后普通重复事件恢复发送或绕过用尽/暂停限制；仅保留目标与哈希，不保留正文。这些指纹会持续增长，不由历史保留天数删除。

## 验证与范围

覆盖 SDK 单次调用、异常分类、过期租约禁止重发、管理员确认、旧表迁移、源消息变化、配置变化、并发保留、重启与取件恢复、退避下限、暂停和次数用尽。浏览器覆盖待核查操作和重试设置，并回归 P2/P3。

本轮范围为不确定状态核查及有界重试的可靠性开发。真实 Telegram/外部通知发送和生产 VPS 升级需在部署环境验收；本轮不对生产账号实际发送。历史导出和恢复通知留作后续工作。

## 部署验收与回滚

升级前停机备份整个 data 目录。P4 增加待核查状态，旧版不能完整识别它；回滚应同时恢复升级前的完整停机备份，不能仅换回旧镜像继续共用已经升级的数据库。

部署后先保持自动重试关闭，用测试频道/Bot 检查：单条文本、媒体 forward/copy、115 链接提取；重复消息不重复投递；重启后成功去重保留；失败记录的人工核查；启用小次数策略后临时拒绝的排期和暂停。待核查确认必须实际查看 Telegram 目标聊天，不能凭错误名称确认未送达。记录后台接受发送不代表外部转存 Bot 处理成功。

## 管理 API 与持久状态

以下接口均要求管理员会话和同源保护：

| 接口 | 用途 |
| --- | --- |
| `GET/PUT /api/relay/retry-policy` | 查看/保存默认关闭的全局策略 |
| `POST /api/relay/resolve` | 携带 destination、fingerprint、attempt、decision（sent/not_sent）、confirmation=checked_destination 提交核查 |
| `POST /api/relay/retry-control` | 携带 destination、fingerprint、attempt、paused 暂停或恢复单条排期 |
| `POST /api/relay/retry` | 复用原人工重试，待核查记录必须先确认 |

`relay_deliveries` 追加分类、租约、来源/配置摘要、排期、配额和核查字段；`relay_reviews` 保存各次人工确认；`relay_suppressed` 保存清理过的失败拦截指纹。均原位追加，不重建主数据库、不存消息正文。队列领取令牌只在服务端传递，历史 API 不返回。
